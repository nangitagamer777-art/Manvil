# CVE-2023-26083 Notes

Timeline stream leak of kernel pointers through the
KBASE_IOCTL_TLSTREAM_ACQUIRE ioctl. Any unprivileged process on a
vulnerable kernel can read internal kernel addresses from the GPU
driver.

## Value for Manvil

### Timeline stream purpose

The timeline stream is a diagnostic and profiling facility. The kernel
serializes events into a ring buffer, and a userspace reader consumes
them by calling read on a file descriptor returned by the ioctl.

### Access control

Access is controlled by BASE_CONTEXT_CREATE_FLAG_MONITOR (bit 4) in the
context create flags. Without the flag, the ioctl should fail. The
vulnerability is that the check was missing on some kernel versions.

Manvil does not request the monitor flag. If the timeline stream is used
for diagnostics, the client application must have a context created with
BASE_CONTEXT_CREATE_FLAG_MONITOR set.

Note that bit 4 overlaps with the MMU group ID bit range (bits 3-6). The
monitor flag is a special case handled by the kernel, not part of the
MMU group ID. Manvil should not set both in the same context.

### Packet format

The stream emits packets in this layout:

  [packet header]   8 bytes
  [message id]      u32
  [timestamp]       u64
  [payload]         variable, depends on message id

The packet header contains fields that identify the packet family,
class, type, stream, and length. The example output shows a header of
the form family=TL class=OBJ type=HEADER stream=1 len=NNNN.

Summary packets (type=SUMMARY) contain multiple messages concatenated.

### Message payload format

Each message id maps to a specific payload layout. The reference
implementation records formats as strings of type codes:

  p   pointer, 8 bytes
  I   unsigned 32-bit integer
  pp  two pointers
  pI  pointer followed by u32
  pII pointer followed by two u32
  ppI two pointers followed by u32

The payload size is derivable from the format string and is also stored
explicitly in the format table.

### Messages observed

The JM variant of the stream emits these message types (among others):

  KBASE_TL_NEW_CTX            new kbase_context
  KBASE_TL_NEW_GPU            new kbase_gpu
  KBASE_TL_NEW_LPU            new kbase_lpu
  KBASE_TL_NEW_ATOM           new atom
  KBASE_TL_NEW_AS             new address space
  KBASE_TL_DEL_CTX            context destroyed
  KBASE_TL_LIFELINK_LPU_GPU   relationship between LPU and GPU
  KBASE_TL_LIFELINK_AS_GPU    relationship between AS and GPU

The CSF variant emits different messages. From other disclosures the
following CSF messages are known:

  KBASE_TL_KBASE_NEW_KCPUQUEUE
  KBASE_TL_KBASE_KCPUQUEUE_ENQUEUE_FENCE_WAIT
  KBASE_TL_KBASE_KCPUQUEUE_ENQUEUE_CQS_WAIT
  KBASE_TL_KBASE_KCPUQUEUE_ENQUEUE_CQS_SET

A full list of CSF messages requires reading the kernel source tree
files mali_kbase/tl/mali_kbase_tracepoints.h and
mali_kbase/tl/mali_kbase_tracepoints.c.

### VERSION_CHECK ioctl difference

The disclosure targets a JM kernel (Android 8.1, kernel 3.18) and uses
ioctl 0 for KBASE_IOCTL_VERSION_CHECK. Modern CSF kernels use ioctl 52.

A driver that wants to support both should probe ioctl 52 first, then
fall back to ioctl 0. This matches the behavior documented in the
PanVK kbase fork.

## Value for Manvil

Medium. Provides the packet format for the timeline stream and confirms
the VERSION_CHECK ioctl difference between JM and CSF. The message list
is specific to JM and is not directly used by Manvil, but it helps
understand the general structure.

## Non-reusable content

The exploit itself and the target device details are not recorded.
